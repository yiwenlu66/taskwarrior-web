# Browser/server contract

The server executes the installed Taskwarrior CLI (no shell) against the environment's TASKRC/TASKDATA. All JSON errors use `{ "error": "human-readable message" }` with non-2xx status.

- `GET /api/meta` → `{version, defaultReport, reports:[{name,description,columns:string[],labels:string[],sort,filter}], projects:string[], tags:string[], contexts:string[], attributes:string[], priorities:string[]}`. Read installed report configuration; exclude internal/non-list reports if necessary. Additional metadata includes printEmptyColumns (boolean) and UDA definitions where supported. No personal config is bundled.
- `GET /api/tasks?report=next&filter=<Taskwarrior filter>` → `{tasks:Task[], report:{name,description,columns,labels,sort,filter}, revision:string, context:string}`. Tasks are normal Taskwarrior export objects (UUID, numeric ID, description, status, project, priority, urgency, dates, tags, annotations, arbitrary UDAs). Apply report's configured filter, context and sort; explicit browser filter is additional. On Taskwarrior 3 use `task <extra-filter> export <report>` with a trusted report.filter override stripping limit:* so the native engine retains sorting. Never append tokens after the report name: Taskwarrior 3 silently discards report filtering in that shape. UUID is the required mutation/refresh identity; numeric IDs are optional ephemeral display values (completed/deleted tasks may lack positive IDs). Display a short UUID fallback rather than inventing IDs. Return counts based on actual results. Same-view refresh keeps the focused UUID; if it disappears, retain the nearest surviving row at the previous index rather than jumping to the first row.
- `POST /api/command` JSON `{command:string, uuids?:string[], report?:string}` → `{output:string, changed:boolean, report?:string, filter?:string}`. `command` includes optional leading colon. Web command aliases (a superset of VIT's ex grammar): `a/add`, `m/modify`, `d/done`, `D/delete`, `b/toggle/start/stop` (toggle partitions fresh selected tasks into active/inactive groups), `A/annotate`, `u/undo`, `r/<report>`, `f/filter`, `context <name|none>`, `denotate` and `sync` where supported. Bare-key VIT actions use b to toggle start/stop, Space to move down, P priority, p project, T tags, w wait, c context, E denotate, S sync; :m is an explicit web extension requested by the user. Selected tasks are addressed by UUID, not changeable numeric IDs. `:m due:tomorrow` modifies selection. `:r next` and `:next` switch report; `:f +tag` sets filter. Only explicit supported task commands, not arbitrary shell/config/execute/import commands. Changes requiring selection fail if selection is empty. Done, delete and start/stop use VIT-style browser confirmation; undo follows VIT's direct u action. Backend sets confirmation=no for noninteractive operation after the browser action. Never silently widen an empty filter/selection. Task errors are surfaced with output. The optional numeric tiebreak UDA supports `tiebreak 1` and `tiebreak -1` for the user's + / - shortcuts: absent/noninteger defaults to 9, new value clamps to 0..18, unchanged values cause no write.
- `GET /api/events` → Server-Sent Events. `event: change`, `data: {"revision":"..."}` on database/config changes. `event: ready` initially. Periodic keepalive comments. Reconnects supported by EventSource; frontend performs full read on ready/reconnect. Taskwarrior 3 SQLite/WAL plus Taskwarrior 2 files are fingerprinted as bytes; never issue SQL or write database files directly. Revision independent of reads so CLI export does not trigger perpetual loop.
- `GET /api/health` → `{ok:true, version:string}`.

Static production frontend is served from `dist/` on same origin. Vite development proxies `/api` to server. Date expression interpretation belongs to Taskwarrior; completion descriptions explain examples, not a replacement date parser.
