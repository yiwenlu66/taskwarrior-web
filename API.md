# Browser/server contract

The server executes the installed Taskwarrior CLI (no shell) against the environment's TASKRC/TASKDATA. All JSON errors use `{ "error": "human-readable message" }` with non-2xx status.

- `GET /api/meta` → `{version, defaultReport, reports:[{name,description,columns:string[],labels:string[],sort,filter}], projects:string[], tags:string[], contexts:string[], attributes:string[], priorities:string[]}`. Read installed report configuration; exclude internal/non-list reports if necessary. No personal config is bundled.
- `GET /api/tasks?report=next&filter=<Taskwarrior filter>` → `{tasks:Task[], report:{name,description,columns,labels,sort,filter}, revision:string, context:string}`. Tasks are normal Taskwarrior export objects (UUID, numeric ID, description, status, project, priority, urgency, dates, tags, annotations, arbitrary UDAs). Apply report's configured filter, context and sort; explicit browser filter is additional. Tasks must have usable numeric IDs (export's ID behavior varies). Return counts based on actual results.
- `POST /api/command` JSON `{command:string, uuids?:string[], report?:string}` → `{output:string, changed:boolean, report?:string, filter?:string}`. `command` includes optional leading colon. VIT aliases: `a/add`, `m/modify`, `d/done`, `D/delete`, `s/start/stop`, `A/annotate`, `u/undo`, `r/<report>`, `f/filter`, `context <name|none>`, `denotate` where supported. Selected tasks are addressed by UUID, not changeable numeric IDs. `:m due:tomorrow` modifies selection. `:r next` and `:next` switch report; `:f +tag` sets filter. Only explicit supported task commands, not arbitrary shell/config/execute/import commands. Changes requiring selection fail if selection is empty. Delete and undo have browser confirmation; backend sets confirmation=no for noninteractive operation. Never silently widen an empty filter/selection. Task errors are surfaced with output.
- `GET /api/events` → Server-Sent Events. `event: change`, `data: {"revision":"..."}` on database/config changes. `event: ready` initially. Periodic keepalive comments. Reconnects supported by EventSource; frontend performs full read on ready/reconnect. Taskwarrior 3 SQLite WAL plus Taskwarrior 2 files are monitored; do not open database directly. Revision independent of reads so CLI export does not trigger perpetual loop.
- `GET /api/health` → `{ok:true, version:string}`.

Static production frontend is served from `dist/` on same origin. Vite development proxies `/api` to server. Date expression interpretation belongs to Taskwarrior; completion descriptions explain examples, not a replacement date parser.
